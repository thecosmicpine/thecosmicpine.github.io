라우터 하나에 전문 서브에이전트 여러 개를 붙인 구조는 AI 에이전트를 만들 때 가장 흔히 고르는 설계다. 그런데 Anthropic이 10월 22일 낸 가이드 「Building agents: When to fold subagents into your main agent loop」는 그 서브에이전트 상당수를 메인 루프 하나로 합치는 편이 품질도 낫고 더 싸고 빠른 경우가 많다고 말한다. 이 글을 읽으면 지금 만든 에이전트에서 어떤 서브에이전트를 남기고 어떤 것을 합칠지 판단하고, 합치는 작업을 어떤 순서로 해야 하는지 알 수 있다.

{: .summary }
> - 서브에이전트를 남길 이유는 **세 가지**뿐이다: 컨텍스트가 넘쳐 성능이 떨어질 때, 병렬 작업에 새 컨텍스트가 필요할 때, 도구 고르기가 헷갈릴 때.
> - 나머지는 **스킬(절차)과 도구(동작)**로 바꿔 메인 루프 하나가 필요할 때만 불러오게 한다.
> - 합칠 때는 **한 번에 하나씩**, 골든 예제 10개짜리 평가라도 먼저 만들고 점수가 떨어질 때만 되돌린다.

## 왜 '하나의 루프'를 말하나: 조직도를 닮은 에이전트

가이드는 큰 회사에서 에이전트를 만들 때 반복되는 실패를 짚는다. 제품마다 팀이 따로 있으니 팀마다 자기 에이전트를 만들고, 중앙 플랫폼 팀이 그 위에 오케스트레이터를 얹는다. 그러면 에이전트 구조가 회사 조직도를 그대로 닮게 된다(가이드는 이를 콘웨이의 법칙이라고 부른다).

이 구조에서 생기는 문제로 가이드는 다섯 가지를 든다. 에이전트끼리 주고받는 사이에 맥락이 빠지고, 주인 없는 서브에이전트가 수백 개로 불어나고, 팀마다 한 문장씩 보탠 시스템 프롬프트가 서로 부딪히고, 팀별 평가가 자기 일에만 맞춰져 전체 품질이 안 보이고, 단계가 많아 느려진다. 한 고객은 멀티 에이전트 구성과 단일 에이전트 루프를 비교해 후자가 약 2배 빨랐다고 한다.

가이드가 단일 루프를 권하는 근거는 세 가지다. 같은 컨텍스트 안에서 앞 단계 결과를 다 본 모델이 요약만 넘겨받는 서브에이전트보다 더 잘 연결한다. 스킬과 도구를 필요할 때만 펼치는 '점진적 공개' 덕분에 프롬프트가 한없이 길어지지 않는다. 그리고 Opus 4.5부터 모델이 한 루프 안에서 다룰 수 있는 일이 예상보다 많아졌다.

## 남겨야 할 서브에이전트, 합쳐도 되는 서브에이전트

가이드는 서브에이전트를 없애라는 게 아니라고 분명히 한다. 검증, 병렬 작업, 권한을 나눠야 하는 곳에서는 여전히 쓸모가 있고, Anthropic 자신도 멀티 에이전트 리서치 시스템을 쓴다. 다만 아래 세 경우가 아니라면 합쳐 볼 후보라는 것이다.

~~~mermaid
flowchart TD
  A[서브에이전트 하나] --> B{컨텍스트 과부하?}
  B -- 예 --> K[남긴다·도구로 호출]
  B -- 아니오 --> C{병렬·새 컨텍스트?}
  C -- 예 --> K
  C -- 아니오 --> D{도구 고르기 혼란?}
  D -- 예 --> K
  D -- 아니오 --> F[스킬+도구로 합친다]
~~~

남기기로 한 서브에이전트도 대화를 통째로 넘기는 대신 메인 에이전트가 '도구처럼' 부르게 하라고 가이드는 권한다. 그래야 메인 에이전트가 사용자와 대화를 계속 붙잡고, 서브에이전트 결과를 실제 데이터와 맞춰 볼 수 있다. 서브에이전트가 사용자와 직접 말해야 할 때만 완전히 넘긴다.

{: .interpret }
세 조건은 모두 "측정해서 확인된 문제"를 요구한다. "이 팀 일이니까 따로"라는 이유는 목록에 없다. 결국 서브에이전트를 나누는 기준을 조직에서 컨텍스트로 바꾸라는 말에 가깝다.

## 합친 뒤의 모양: 스킬·도구·지식 베이스

가이드가 그리는 목표는 모델 하나, 컨텍스트 창 하나가 도는 열린 도구 루프다. 모델이 한 턴에 도구 호출을 묶어서 내면 하네스가 병렬로 실행해 결과를 그대로 돌려주고, 모델이 다음 단계를 정한다. 계획을 세우는 모델이 실행도 하니 중간에 계획을 고칠 수 있다는 점이 오케스트레이터 구조와 가장 크게 다르다. 턴·비용 한도와 쓰기 승인 같은 강제 장치는 하네스에 둔다. 가이드가 링크한 Claude API의 작업 예산(task budget, 베타)은 루프 전체에 쓸 토큰을 모델에게 알려 주지만 권고일 뿐이라, 실제 상한은 `max_tokens`와 하네스 쪽 한도로 걸어야 한다.

서브에이전트가 맡던 일은 성격에 따라 셋으로 나눠 옮긴다.

| 옮길 곳 | 맞는 일 | 예 |
|---|---|---|
| 도구(MCP) | 동작하기, 실시간 데이터 읽기, 정해진 형식으로 돌려주기 | 주문 조회, 권한 확인 |
| 스킬 | 팀이 일하는 절차·규칙·판단 기준 | 전문 서브에이전트 프롬프트에 있던 단계 |
| 지식 베이스 | 가끔만 필요한 참고 자료 | 정책, 지표 정의, 제품 사양 |

도구는 API 하나에 하나씩이 아니라 사용자 의도 단위로 묶으라고 한다. 도구가 30~50개를 넘으면 고르기가 흔들리기 때문이다. 이때 Claude API의 도구 검색(tool search)을 쓰면 도구 정의를 전부 보내되 `defer_loading: true`를 붙인 것은 필요할 때만 컨텍스트에 올라온다. 공식 문서 기준 한 요청에 지연 로딩 도구를 1만 개까지 둘 수 있고, 자주 쓰는 3~5개는 지연 로딩하지 말라고 권한다.

## 합치는 순서: 평가 먼저, 하나씩, 결과가 바뀐 과제까지

가이드가 제시하는 이행 순서는 다음과 같다.

1. 중앙 팀이 끝에서 끝까지 보는 평가 세트를 만든다. 골든 예제 10개로도 시작할 수 있다
2. 오케스트레이터가 있는 동안은 답변 품질과 함께 '맞는 서브에이전트를 골랐나'도 잰다
3. 늘 같이 불리거나 같은 데이터를 만지는 서브에이전트 쌍부터 하나로 묶는다
4. 남길 서브에이전트는 메인 에이전트가 도구로 부르게 바꾸고 기준 점수를 잡는다
5. 서브에이전트 하나의 프롬프트는 스킬로, API 호출은 MCP 도구로 옮긴다
6. 합치기 전후 점수를 비교하고, 합친 쪽이 낮을 때만 서브에이전트로 되돌린다
{: .steps }

{: .warning }
최종 점수만 보면 안 된다. Anthropic이 예제 고객지원 에이전트로 시험했을 때 하나를 합치자 지연은 줄었지만, 주문 조회 도구를 쥔 메인 에이전트가 배송 담당에게 묻지 않고 혼자 답해 원래 통과하던 과정이 깨졌다. 이 오류는 두 번 중 한 번만 나타났다. 실제로 함께 도는 에이전트 묶음마다 과제를 넣고, 과제마다 여러 번 돌려야 한다.

이 작업을 돕도록 Anthropic은 Apache-2.0 라이선스의 이행 키트(`anthropics/single-agent-loop-kit`)를 공개했다. 키트의 `skill` 폴더를 내 에이전트 저장소의 `.claude/skills/`에 복사하고 Claude Code에서 실행을 요청하면, 서브에이전트마다 합치기·묶기·도구로 부르기·남기기 판정을 보여 준 뒤 한 번에 하나씩 바꾸며 평가한다. 유료 평가를 돌리기 전에는 예상 토큰과 함께 멈춰서 묻는다. API 키 없이 돌려 보는 예제(`examples/support-desk`, 라우터 1개와 서브에이전트 6개)도 들어 있다.

{: .tip }

> - [ ] 골든 예제 10개와 '반드시 지킬 규칙' 과제로 평가 세트를 먼저 만든다
> - [ ] 키트 README대로 과제 10개·반복 2~3회로 작게 시작해 비용을 확인한다

키트 README는 스스로 유지보수하지 않는 참고 구현이라고 밝히고, 일부 단계와 완성본 예제는 실제 모델로 돌려 보지 않았다고 적어 두었다. 그대로 믿고 쓰기보다 갈라 와서(fork) 내 사정에 맞게 고쳐 쓰는 출발점으로 보는 편이 맞다.

## 마무리

가이드의 마지막 문장은 특정 구조가 아니라 원칙을 남긴다. 재고, 한 번에 하나만 바꾸고, 버티는 것만 남기라는 것이다. 모델이 바뀔 때마다 하네스가 대신하던 판단이 모델 쪽으로 넘어가니, 지금 합치지 못한 서브에이전트도 다음 모델에서는 다시 재 볼 이유가 생긴다. 평가 세트를 먼저 만들어 두는 게 이번 한 번이 아니라 앞으로 모델을 갈아탈 때마다 쓰는 자산이 되는 이유다.
