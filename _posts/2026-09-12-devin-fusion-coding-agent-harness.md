## 이 문서가 다루는 문제

소프트웨어 작업의 난이도는 최초 요청만으로 판단하기 어렵다. `버그를 고쳐 줘`라는 짧은 요청도 조사해 보면 한 줄 수정일 수 있고, 제품 구조를 다시 설계해야 하는 문제일 수도 있다. 따라서 요청을 받자마자 저렴한 모델과 고성능 모델 중 하나를 고르는 단순 라우팅은 잘못된 선택을 할 수 있다.

작업 중간에 모델을 바꾸는 방법도 비용 문제를 완전히 해결하지 못한다. Cognition은 이 방식이 프롬프트 캐시를 깨뜨려 고성능 모델의 비용을 다시 발생시킬 수 있다고 설명한다. Fusion은 모델 하나를 고르는 대신, 역할이 다른 두 에이전트를 같은 세션에 계속 유지하는 방식으로 이 문제를 다룬다.

## 핵심 개념

**코딩 에이전트 하네스**는 모델이 소프트웨어 작업을 수행하도록 감싸는 운영 구조다. 계획, 도구 호출, 컨텍스트 유지, 역할 분담, 구현, 테스트와 리뷰의 순서를 결정한다. 같은 모델을 사용하더라도 하네스가 다르면 작업 방식과 비용, 결과가 달라질 수 있다.

Fusion에서는 두 모델을 선택한다.

- **Lead:** 프론티어 모델을 사용하며 계획, 모호한 요구의 해석, 위임과 최종 리뷰를 맡는다.
- **Sidekick:** 비용 효율적인 모델을 사용하며 코드 탐색, 구현, 테스트와 결과 보고를 맡는다.

Cognition은 Fable 5.1과 SWE-2 조합을 권장한다. 이 권장은 자사 평가에 기반한 제품 제공자의 판단이며, 모든 저장소와 작업에서 최적이라는 독립 검증 결과는 아니다.

Fusion이 제시하는 비용 단위도 중요하다. 토큰 하나의 가격보다 **작업 하나를 끝내는 총비용**을 봐야 한다는 주장이다. 단가가 높은 모델이라도 더 일찍 정확하게 위임하고, 좋은 브리프를 작성하며, 재작업을 줄인다면 전체 비용은 낮아질 수 있다.

## 작동 원리

1. 사용자의 요청은 Lead가 받는다.
2. Lead가 저장소와 요구사항을 해석하고 계획을 세운다.
3. 위임할 작업의 목표, 제약, 성공 기준을 담은 브리프를 만든다.
4. Sidekick이 자체 컨텍스트와 도구를 사용해 탐색, 구현, 테스트를 수행한다.
5. Sidekick은 전체 작업 기록 대신 결과와 필요한 근거를 Lead에 돌려준다.
6. Lead가 결과를 검토하고 문제를 발견하면 피드백을 주거나 작업을 직접 회수한다.
7. 검토를 통과한 결과를 Lead가 사용자에게 전달한다.

두 에이전트는 전체 대화와 모든 도구 출력을 서로 복사하지 않는다. 브리프, 결과, 피드백만 교환하고 각자의 지속적인 컨텍스트를 유지한다. Cognition은 이 구조가 프롬프트 캐시를 활용하면서도 프론티어 모델이 계속 책임을 지게 한다고 설명한다.

## 구조와 흐름

```text
사용자 요청
    ↓
Lead: 요구 해석·계획·성공 기준
    ↓ 브리프
Sidekick: 탐색·구현·테스트
    ↓ 결과와 근거
Lead: 리뷰·수정 지시·작업 회수
    ↓
사용자에게 최종 결과 전달
```

이 역할 경계는 모든 모델 조합에서 같지 않다. Cognition은 조합별로 다음 요소를 조정한다고 밝힌다.

- 약한 Sidekick에는 더 구체적인 브리프를 주고, 강한 Sidekick에는 구현 판단의 여지를 더 준다.
- 강한 Sidekick의 이의 제기는 Lead 계획의 오류를 찾는 데 도움이 될 수 있지만, 약한 Sidekick에 같은 자유를 주면 성능과 비용이 나빠질 수 있다.
- 계획에 직접 영향을 주는 초기 탐색은 약한 Sidekick에 맡기지 않고, 강한 Sidekick은 초기 탐색을 지원하게 할 수 있다.

이는 Lead와 Sidekick을 한 쌍으로 지정하는 것만으로 충분하지 않으며, 위임 규칙 자체도 모델 조합에 맞춰야 한다는 뜻이다. Cognition은 이 경계를 계속 연구 중이라고 명시한다.

## 적용 시나리오

다음은 Fusion의 작동 원리를 버그 수정에 적용해 재구성한 가상 시나리오다.

- **배경:** 결제 서비스 팀이 간헐적으로 중복 요청이 처리되는 버그를 조사한다.
- **목표:** 원인을 특정하고 기존 동작을 깨뜨리지 않는 최소 수정안을 만든다.
- **입력:** 버그 설명, 재현 로그, 관련 저장소와 테스트 명령.
- **단계:** Lead가 모호한 조건과 성공 기준을 정리한다 → Sidekick에 관련 코드 탐색과 재현 테스트 작성을 위임한다 → Sidekick이 구현과 테스트 결과를 보고한다 → Lead가 경쟁 조건과 회귀 가능성을 검토한다 → 필요하면 수정 지시를 내리거나 직접 작업을 회수한다.
- **기대 결과:** 변경된 코드, 재현 테스트, 기존 테스트 결과와 Lead의 최종 검토가 함께 제시된다.
- **실패 조건:** 재현 로그가 부족하거나 Sidekick이 핵심 동시성 경로를 놓치거나, Lead가 결과를 충분히 검토하지 않으면 잘못된 수정이 통과할 수 있다.
- **검증:** 수정 전에는 재현 테스트가 실패하고 수정 후에는 통과하는지, 기존 테스트에 회귀가 없는지, 변경 내용이 명시된 성공 기준을 충족하는지 확인한다.

## Hands-on

공식 게시물은 Devin CLI 설치 명령과 Fusion의 개념을 제공하지만, 비대화형으로 Fusion을 선택하고 Lead·Sidekick을 지정하는 전체 명령은 공개하지 않는다. 따라서 아래 절차는 설치 가능 여부와 제품 화면에서 구조를 관찰하는 수준이다. 실제 설치와 로그인은 수행하지 않았으며 공식 게시물 기준으로만 확인했다.

### 1. 버전

- **런타임:** 해당 없음 — 공식 게시물에 별도 런타임 버전이 제시되지 않았다.
- **도구·라이브러리:** Devin CLI, 정확한 버전 미표기. Fusion 공개 글의 게시일은 2026-09-11이다.

### 2. 전제조건

- **계정·키·권한:** Devin 계정과 로그인 권한이 필요할 수 있으나, 원문에는 인증 절차와 요금제 조건이 구체적으로 적혀 있지 않다.
- **운영체제·외부 서비스:** 공식 설치 명령은 `curl`과 셸을 전제로 한다. 지원 운영체제 범위는 원문만으로 확인할 수 없다. 외부 설치 스크립트를 실행하므로 실행 전에 내용을 검토해야 한다.

### 3. 설치

공식 게시물이 제공하는 최소 설치 명령은 다음과 같다.

```bash
curl -fsSL https://cli.devin.ai/install.sh | bash
```

외부 스크립트를 즉시 셸로 전달하는 명령이므로, 신뢰할 수 있는 환경인지 확인한 뒤 사용한다. 설치 위치, 제거 방법과 고정 버전 설치법은 원문에 없다.

### 4. 최소 실행

```text
1. 설치된 Devin CLI를 실행하고 계정 인증을 완료한다.
2. 모델 선택 화면에서 Fusion을 선택한다.
3. Lead와 Sidekick 모델을 지정한다.
4. 테스트 저장소에서 범위가 작은 코드 조사·수정 요청을 입력한다.
```

정확한 실행 명령과 비대화형 옵션은 공식 게시물에 제시되지 않아 문서만으로 재현할 수 없다. 제품 기능이나 플래그를 추정해 추가하지 않았다.

### 5. 예상 결과

사용자는 프론티어 Lead와 비용 효율적인 Sidekick을 선택할 수 있어야 한다. 작업 중에는 Lead가 계획과 리뷰를 맡고 Sidekick이 탐색·구현·테스트를 수행한 결과가 세션에 반영되어야 한다. 에이전트별 내부 컨텍스트와 캐시 상태가 화면에 노출되는지는 원문에 설명되어 있지 않다.

### 6. 검증

```text
- 선택한 Lead와 Sidekick이 세션 설정에 표시되는지 확인한다.
- 요청에 적은 성공 기준과 최종 변경·테스트 결과를 대조한다.
- Lead의 리뷰 또는 Sidekick에 대한 피드백이 세션 기록에서 관찰되는지 확인한다.
```

비용 절감률이나 프롬프트 캐시 효과는 단일 로컬 실행으로 검증할 수 없다. 같은 작업을 충분한 표본으로 반복하고 모델별 비용과 성공률을 통제해 비교해야 한다.

### 7. 대표 오류

- **증상:** 설치 명령이 실패한다.
- **원인:** 네트워크 차단, `curl` 또는 호환 셸 부재, 설치 서버 접근 실패 가능성이 있다.
- **해결:** 네트워크와 필수 명령의 존재를 확인하고, 설치 스크립트 내용을 검토한다. 원문에는 운영체제별 해결 절차가 없다.

- **증상:** CLI에서 Fusion 또는 원하는 모델 조합을 찾을 수 없다.
- **원인:** CLI 버전, 계정 권한, 제공 지역 또는 제품 정책 차이일 수 있으나 원문만으로 원인을 확정할 수 없다.
- **해결:** CLI 버전과 계정의 기능 제공 여부를 공식 지원 채널에서 확인한다. 확인되지 않은 플래그로 기능을 강제하지 않는다.

## 읽을 때 경계

Cognition은 Artificial Analysis 및 Vals AI와 함께 여러 코딩 벤치마크에서 Fusion을 평가했다고 밝힌다. Fable 5.1 또는 GPT-6 Astra를 Lead로, SWE-2를 Sidekick으로 사용한 결과 비용을 낮추면서 프론티어 수준의 성능을 유지했으며, 다른 모델 하네스보다 최대 39% 효율적이라고 주장한다. 이 수치와 비교는 Cognition 게시물에 제시된 평가 결과이며 독립 재현 결과가 아니다.

게시물의 표에서는 벤치마크와 모델 조합에 따라 비용 감소 폭과 점수 변화가 달랐다. 일부 조합은 비용이 줄면서 점수가 소폭 낮아졌고, 다른 조합은 점수가 높아졌다. 따라서 “최대 39%”를 모든 작업의 보편적인 절감률로 해석해서는 안 된다.

Cognition은 Lead를 Opus 4.8에서 토큰당 명목 가격이 두 배인 Fable 5로 바꾸자 FrontierCode 점수가 높아지고 평균 세션 비용은 9% 낮아졌다고 보고한다. Fable이 더 일찍 위임하고 더 좋은 브리프를 작성한 반면 Opus는 Sidekick을 세밀하게 통제하고 작업을 다시 수행한 것이 이유라는 자체 분석이다.

Sidekick 비교에서도 Cognition은 GPT-5.6 Luna보다 SWE-2의 표시 토큰 가격이 275% 높았지만, Astra 기반 Fusion의 FrontierCode 결과가 `62.0 / $2.39`에서 `63.4 / $2.34`로 바뀌었다고 보고한다. 이 역시 특정 하네스, 벤치마크와 설정에서 얻은 자체 측정이며 실제 저장소의 비용을 보장하지 않는다.

Fusion은 프론티어 모델이 항상 책임을 진다는 구조적 장점이 있지만, Lead의 계획이나 리뷰 자체가 틀리면 오류를 막지 못한다. 두 에이전트의 병렬 유지 비용, 제품 접근 조건, 내부 프롬프트, 모델 조합별 튜닝 방법도 공개 글만으로는 완전히 재현할 수 없다.

## 남는 한 줄

Fusion의 핵심은 저렴한 모델로 단순 교체하는 것이 아니라, 프론티어 모델이 계획과 검토의 책임을 유지한 채 실행 작업을 분리하는 하네스 설계다.
