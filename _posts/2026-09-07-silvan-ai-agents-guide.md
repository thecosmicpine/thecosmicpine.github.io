## 왜 한 번에 안 읽혔나

제목부터 “완전 가이드 · 오늘부터 수익화”라서, 레시피처럼 따라가게 된다. 그런데 본문은 **정의 → 파는 말 → 레벨 0–5 → 실수 → 스택**이 한 줄에 겹친다.

**정의와 판매 문장이 같은 단락에 있다.**  
에이전트 = LLM + tool calling + 실행 루프 + 메모리/상태 — 그 옆에 “SLA를 팔아라”, “GPT를 붙였다고 말하지 마라”가 온다. 기술 정의인지 영업 조언인지, 첫 읽기에는 경계가 흐리다.

**레벨이 난이도처럼 보이지만, 제품화 단계에 가깝다.**  
0은 부품, 1은 이번 주 청구, 2는 패키지, 3은 무인 운영, 4는 레거시·멀티에이전트, 5는 자기 시스템. “더 똑똑한 에이전트” 축이 아니라 **더 팔고, 더 오래, 더 비싸게** 가는 축으로 읽히는데, 목차만 보면 커리큘럼처럼 보인다.

**스택 목록이 레시피처럼 느껴진다.**  
끝에 n8n, LangGraph, Pinecone, LangSmith가 카테고리별로 나온다. 원문은 “카테고리별 지도”인데, 따라 하기 체크리스트로 읽으면 막힌다.

데모 스레드는 화려하고, “그래서 내일 무엇을 팔지?”는 남는 글이다. silvan은 **지도**를 주려 했고, 나는 **제품화의 계단**으로 다시 짜서 읽었다.

## 내가 잡은 핵심 주장

한 줄로 압축하면 이렇다.

**에이전트는 챗봇이 아니라, 도구를 고르고 결과를 보고 다시 고르는 루프다. 팔 때는 모델 이름이 아니라 측정 가능한 SLA를 판다.**

원문 TL;DR이 이미 그 뼈대다.

1. **네 조각이 없으면 에이전트가 아니다.** LLM, tool calling, 실행 루프, 메모리/상태.
2. **첫 매출은 100% 자율이 아니라, 결정론적 자동화 + LLM 결정 지점 하나.**
3. **RAG·observability·프롬프트 버전 관리**가 “데모 → 제품”을 가른다.
4. **높은 티켓은 멀티에이전트 + 레거시 통합** — 노코드가 안 들어가는 곳.

“AI”라는 단어로 팔지 말고, 응답 시간·해결률·절약한 사람 시간으로 팔라는 문장이, 기술 정의보다 더 오래 남았다.

## 레벨을 제품화 계단으로 읽기

원문 레벨을 커리큘럼이 아니라 **무엇을 팔 수 있게 되는지**로 다시 보면, 에스컬레이션이 보인다. (아래 분할은 내 읽기이며, 원문 번호와 1:1 대응을 강제하지는 않는다.)

**부품을 안다 (레벨 0).**  
루프, function calling, MCP, 메모리, RAG. 유스케이스는 시장 크기보다 **이미 아는 도메인**에서. 측정 가능한 결과를 아키텍처보다 먼저. 무료 포트폴리오보다 유료 첫 고객 — 데모 피드백과 프로덕션 피드백이 다르다는 경고.

**한 점의 지능으로 판다 (레벨 1).**  
webhook → LLM 분류 → 결정론적 액션. 의도 분류 응대, 출처 인용 RAG, 리드 스코어링, 상태 기반 팔로업. 공통점은 “전체 자율”이 아니라 **한 임계 결정**. 제안은 “AI 에이전트”가 아니라 병목을 푸는 구체 플로우.

**같은 일을 제품으로 묶는다 (레벨 2).**  
템플릿, 프롬프트·스키마 키트, 산업별 색인 구조, 자기 스택 미니 교육. 설계비를 한 번 받고, 다음 판매는 마진에 가깝게.

**내가 안 눌러도 돈(또는 가치)이 나온다 (레벨 3).**  
모니터링, 리서치 파이프라인, 벤치마크·제휴. 실패 실행을 자기에게 알리지 않으면 고객이 먼저 발견한다 — 이 레벨의 핵심 실수로 원문이 짚는다.

**시스템 통합이 상품이 된다 (레벨 4).**  
ERP/CRM, RPA, 멀티에이전트 그래프, 성숙도 감사, observability를 서비스로. 여기서 티켓이 커지고, 노코드 경쟁이 빠진다. OAuth·서명 webhook·부분 실패를 읽을 수 있어야 한다는 문장이, “시니어 ML”보다 현실적인 자격처럼 읽힌다.

**복제 가능하게 만든다 (레벨 5).**  
git으로 프롬프트·스키마·플로우, 버티컬 템플릿, 포화 전 가격 인상, 고객당 토큰·유지보수·인시던트 대비 매출. “잘 팔린다”와 “남는 사업”을 가르는 장이다.

이렇게 보면 레벨은 모델이 똑똑해지는 순서가 아니라, **판매 단위가 커지고 운영 책임이 깊어지는** 순서다.

## 남기는 것 · 열린 질문

**남기는 것**

| | |
|---|---|
| 정의 | 에이전트 = LLM + tool calling + 루프 + 메모리/상태 |
| 첫 제품 | 결정론적 자동화 + LLM 결정 하나, 첫날부터 청구 |
| 판매 문장 | 모델 통합이 아니라 SLA·지표 |
| 제품의 조건 | RAG 품질, observability, 프롬프트/플로우 버전 관리 |
| 높은 티켓 | 레거시 통합 · 멀티에이전트 · 관측을 서비스로 |
| 흔한 실패 | 긴 프롬프트=에이전트, 한도 없음, 일반 청킹, 과한 멀티에이전트 |

**스택은 레시피가 아니라 내 지도용으로만.**  
모델 API / 에이전트 오케스트레이션(LangGraph, CrewAI 등) / 결정론적 층(n8n·Make·Zapier) / MCP / 벡터 DB / 영속 메모리 / observability·evals / git. 원문이 나열한 카테고리를 그대로 옮긴 것이고, “이 조합으로 하라”는 처방이 아니다.

**열린 질문 (원문이 채우지 않은 빈칸)**

- MCP를 “오늘 배우면 경쟁 우위”라고 했는데, 고객 납품에서 MCP 노출이 실제로 계약·유지보수 비용을 얼마나 줄이는지는 사례 수치가 없다.
- RAG가 “유용함의 80%”라는 표현은 원문 주장이지, 측정 근거는 글 안에 없다.
- 레벨 1→4로 가는 **전환 시점**(몇 고객, 어떤 재계약)은 감각으로만 남아 있다.
- 가격·티켓 크기 숫자도 원문에 거의 없다. “열 명의 레벨 1” 비유만 있다.

해석이 원문과 어긋날 수 있는 지점은 여기다. 나는 레벨을 **제품화 계단**으로 읽었고, silvan은 동시에 **기술 커리큘럼**으로도 짜 두었다.
