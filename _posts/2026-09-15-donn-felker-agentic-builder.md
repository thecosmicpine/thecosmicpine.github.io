## 이 문서가 다루는 문제

소프트웨어 업계에서는 오랫동안 코딩 능력이 제품을 만들 수 있는 사람과 그렇지 않은 사람을 가르는 진입 장벽처럼 작동했다. 원문은 진짜 차이를 만든 역량이 코딩 자체보다 **아이디어를 실제 결과로 바꾸는 실행력**이었다고 본다. 에이전트가 코드 작성과 반복 작업의 비용을 낮추면서 이 실행력이 개발자만의 전유물이 아니게 됐다는 것이 글의 출발점이다.

저자가 관찰한 변화의 범위는 단순한 자동 완성을 넘어선다. 2025년 중반 이후 에이전트가 새로운 SaaS 구축, 대규모 레거시 마이그레이션, 비개발자의 실무 도구 제작에 사용되는 사례를 제시한다. 레거시 작업 사례에서는 사람이 6~8시간 들이던 일을 Skill로 약 10분에 처리했다고 말한다. CFO와 헬스장 사장처럼 전통적인 개발 직군이 아닌 사람도 자신의 문제를 해결하는 도구를 만들 수 있다고 설명한다. 다만 이 수치와 사례는 원문 저자의 경험과 관찰이며, 독립적으로 재현된 생산성 측정값은 아니다.

이 변화는 “엔지니어링과 프로덕트 중 누가 이기는가”라는 경쟁 구도로 설명하기 어렵다. 더 유용한 질문은 **실행 비용이 거의 사라질 때 어떤 가치가 남는가**다. 특정 기술만 깊게 수행하는 초전문화는 실행이 비쌌던 환경에서는 보호막이었지만, 실행이 싸진 환경에서는 오히려 역할의 범위를 제한할 수 있다는 것이 원문의 주장이다.

## 핵심 개념

### 직업 정체성과 Catch-22

`Android Developer` 같은 직업 라벨은 타인에게 전문성을 빠르게 설명하는 사회적 압축 모델이면서, 개인에게는 자기 정체성의 중심이 되기도 한다. AI는 단지 작업 방식을 바꾸는 것이 아니라 이 정체성을 흔든다. 사용하지 않으면 뒤처질 것 같고, 적극적으로 사용하면 자신을 대체할 도구를 스스로 키우는 것처럼 느끼는 Catch-22가 생긴다. 원문은 기술 변화에 대한 불안을 이 모순과 연결한다.

### Agentic Builder

원문이 제안하는 역할은 **Agentic Builder**다. 엔지니어링과 비즈니스 사고를 한 사람이 함께 운용하고, 에이전트를 이용해 아이디어부터 운영 가능한 결과까지 책임지는 실행자다. 엔지니어링 쪽 이름으로는 `Agentic Product Engineer`도 사용한다.

이 역할에서 순수 엔지니어와 순수 아이디어 제안자라는 양극단은 모두 취약하다. 코드를 만들 수 있어도 비용, 출시 시점, 고객 가치, 구매와 자체 개발 사이의 판단을 하지 못하면 사업 결과와 연결되기 어렵다. 반대로 아이디어는 있어도 아키텍처, 버전 관리, 관측 가능성, 가드레일을 이해하지 못하면 복잡성과 운영 위험을 통제하기 어렵다. 따라서 “내 일이 아니다”라고 경계를 긋기보다 문제를 끝까지 해결하는 범위로 역할을 넓혀야 한다는 것이 원문의 방향이다.

### 레버리지 진자

에이전트가 주는 레버리지는 한쪽 직군에 고정되지 않고 과업의 단계에 따라 움직인다.

1. **초기 MVP와 실험:** 프로덕트 담당자나 비기술 직군이 아이디어를 대화로 구체화하고 짧은 시간 안에 작동하는 형태로 만들 수 있어 이들의 실행력이 커진다.
2. **복잡도와 규모가 증가하는 구간:** 코드가 어디에 있는지, 구조가 왜 그렇게 되어 있는지, 비용과 데이터 전송량을 어떻게 관리할지, 어떤 가드레일이 필요한지를 판단해야 하므로 엔지니어링 역량의 가치가 다시 커진다.
3. **반복과 수렴:** 엔지니어가 만든 구조와 가드레일이 시스템에 쌓이면 비기술 담당자도 다시 더 많은 일을 직접 수행할 수 있다. 이후 새 정체 구간에서는 이전보다 짧고 집중적인 엔지니어링 개입이 필요해진다.

원문은 이를 운동에 비유한다. 초보자는 혼자 운동해도 빠르게 좋아지지만, 어느 순간 정체되거나 잘못된 자세로 다칠 수 있다. 트레이너가 자세와 프로그램을 바로잡으면 다시 혼자 진행할 수 있고, 다음 정체에서는 더 짧은 개입으로도 앞으로 나아갈 수 있다.

## 작동 원리

Agentic Builder로의 전환은 두 단계로 작동한다.

첫째, **자신의 숙련을 Skill, 템플릿, 절차, 체크리스트로 코드화한다.** 반복 업무를 매번 직접 수행하는 대신 판단 순서와 완료 기준을 에이전트가 따를 수 있는 형태로 바꾼다. 사람의 역할은 개별 작업을 처리하는 운영자에서 입력, 제약, 품질 기준을 설계하고 결과를 검토하는 오케스트레이터로 이동한다.

둘째, **전문 분야 중심 사고를 시스템 사고로 확장한다.** 엔지니어는 기술적 정답만 찾지 않고 ROI, 유지비, 출시 속도, `buy vs build`를 함께 판단한다. 비기술 직군은 에이전트에게 결과물만 요구하지 않고 구조의 유지·확장 가능성, 코드와 버전의 관리 위치, 장애 관측 방법, 백업과 안전장치를 함께 묻는다.

이 과정의 입력은 반복되는 전문 업무와 작업자의 암묵지다. 처리 단계는 업무 식별, 판단 규칙 추출, 절차 작성, 실제 작업 적용, 결과 검증, 실패 사례를 반영한 규칙 개선 순서다. 출력은 재사용할 수 있는 Skill 또는 체크리스트다. 반복할수록 개인의 숙련이 한 번의 작업이 아니라 다음 작업에도 적용되는 시스템 자산으로 바뀐다.

## 구조와 흐름

Agentic Builder의 작업 구조는 다음 다섯 요소로 나눌 수 있다.

1. **문제와 사업 맥락:** 누가 어떤 문제를 겪는지, 해결하면 비용·매출·속도에 어떤 변화가 있는지 정의한다.
2. **전문 지식:** 작업 순서, 예외, 자주 하는 실수, 품질 기준처럼 사람이 축적한 암묵지를 꺼낸다.
3. **코드화된 절차:** 전문 지식을 Skill, 템플릿, 체크리스트로 바꿔 에이전트가 반복해서 따르게 한다.
4. **기술 가드레일:** 아키텍처, 버전 관리, 백업, 관측, 비용 통제, 파괴적 동작 방지 조건을 둔다.
5. **피드백 루프:** 실제 결과를 검증하고 실패 원인을 절차에 되돌려 다음 실행의 품질을 높인다.

전체 흐름은 `문제 정의 → 전문 지식 추출 → 절차 코드화 → 에이전트 실행 → 사람이 결과 검증 → 규칙 보완`으로 이어진다. 이 흐름에서 에이전트는 책임의 주체라기보다 실행 레버리지다. 무엇을 만들고 어떤 수준을 통과해야 하는지는 사람이 정의한다.

## 적용 시나리오

다음은 원문의 원리를 레거시 라이브러리 마이그레이션 검토에 적용한 가상 시나리오다. 원문에 나온 특정 마이그레이션 성과를 재현한 실제 사례는 아니다.

- **배경:** 한 제품 팀이 여러 저장소에서 오래된 라이브러리를 교체할 때마다 같은 호환성 조사와 리뷰를 반복한다.
- **목표:** 담당자의 판단 기준을 재사용 가능한 Skill로 만들어, 에이전트가 변경 계획을 작성하고 사람이 위험한 결정에 집중하게 한다.
- **입력:** 현재 의존성 목록, 목표 버전의 변경 사항, 영향을 받는 코드, 기존 테스트 명령, 조직의 배포·롤백 규칙.
- **단계:** 반복 업무 선정 → 담당자 인터뷰 → 호환성·테스트·롤백 체크리스트 작성 → 한 저장소에 시범 적용 → 변경안과 테스트 결과 검토 → 누락된 예외를 Skill에 반영.
- **기대 결과:** 마이그레이션마다 확인해야 할 항목, 변경 순서, 완료 조건이 같은 형식으로 정리되고 검토자가 근거와 누락 여부를 추적할 수 있다.
- **실패 조건:** 목표 버전의 변경 사항이 제공되지 않거나, 테스트·롤백 방법이 없거나, 조직 고유의 예외가 인터뷰에서 빠지면 절차가 그럴듯한 일반론에 머물 수 있다.
- **검증:** Skill 없이 작성한 기존 검토 기록과 결과를 비교해 필수 항목의 누락 여부를 확인하고, 저장소의 기존 테스트와 담당자 리뷰를 모두 통과했는지 확인한다.

## Hands-on

이 실습은 특정 제품의 플러그인을 설치하는 작업이 아니라, 자신이 반복하는 전문 업무를 텍스트 기반 Skill과 체크리스트로 코드화하는 절차다. 원문의 “What to Do Next”를 실행 가능한 최소 단위로 풀었다.

### 1. 버전

- **런타임:** 해당 없음 — 실행 코드가 아니라 텍스트 절차를 만드는 실습이다.
- **도구·라이브러리:** 고정 버전 없음 — 대화를 통해 문서를 작성할 수 있는 AI 도구와 일반 텍스트 편집기를 사용한다. 제품별 기능이나 파일 형식에 의존하지 않는다.

### 2. 전제조건

- 반복해서 수행했고 판단 기준을 설명할 수 있는 전문 업무 한 가지.
- 그 업무의 실제 입력 예시, 자주 발생하는 실수, 완료 기준.
- 텍스트 파일을 만들고 결과를 검토할 수 있는 환경.
- 계정·키·특별 권한은 사용하는 AI 도구의 정책에 따른다. 민감한 고객 정보, 비밀 키, 비공개 코드는 입력하지 않는다.

먼저 다음 질문으로 대상을 고른다.

- 남들이 나에게 자주 물어보는 일은 무엇인가?
- 이미 여러 번 했고 다시 수작업으로 하기 싫은 일은 무엇인가?
- 익숙하지만 자꾸 미루는 일은 무엇인가?

### 3. 설치

해당 없음 — 공식 패키지나 CLI가 필요한 실습이 아니다. 사용할 AI 도구와 텍스트 편집기가 이미 준비되어 있으면 별도 설치 없이 진행할 수 있다.

### 4. 최소 실행

선택한 AI 도구에 아래 요청을 입력하고, 질문에 실제 업무 기준으로 답한다.

```text
내가 반복하는 전문 업무를 재사용 가능한 Skill과 체크리스트로 정리해 줘.
한 번에 결론을 만들지 말고, 다음 내용을 하나씩 인터뷰해 줘.

1. 이 Skill을 언제 사용하고 언제 사용하지 않는가
2. 작업에 필요한 입력과 시작 조건
3. 내가 실제로 따르는 판단 순서
4. 자주 발생하는 실수와 중단 조건
5. 완료 기준과 결과 검증 방법

인터뷰가 끝나면 다음 구조로 초안을 작성해 줘.
- 목적과 사용 조건
- 필요한 입력
- 단계별 절차
- 실패·중단 조건
- 완료 체크리스트

주제: 레거시 라이브러리 마이그레이션 검토
```

생성된 초안을 실제로 미뤄 둔 업무 한 건에 적용한다. 매 단계에서 체크리스트의 근거를 남기고, 도구가 수행할 수 있는지 불분명한 작업은 추측하게 두지 말고 가능 여부와 필요한 입력을 먼저 묻는다.

기술 결정을 포함한 업무라면 각 선택에 다음 두 질문을 추가한다.

- 이 선택은 비용, 유지보수 부담, 출시 속도에 어떤 영향을 주는가?
- 지금 직접 만드는 것과 기존 도구를 구매하거나 도입하는 것 중 어느 쪽이 나은가?

비기술 업무를 자동화한다면 다음 항목도 완료 체크리스트에 넣는다.

- 유지·확장 가능한 구조인지
- 결과물과 변경 이력이 어디에서 버전 관리되는지
- 백업과 복구 방법이 있는지
- 실패를 어떻게 발견하고 관측하는지
- 파괴적 동작 전에 사람의 확인을 받는지

### 5. 예상 결과

최소한 다음 항목을 가진 텍스트 문서 한 개가 만들어진다.

- 이 절차를 사용할 조건과 사용하지 않을 조건
- 작업에 필요한 입력
- 순서가 명확한 실행 단계
- 자주 발생하는 실수와 실패·중단 조건
- 관찰 가능한 완료 기준과 검증 체크리스트

첫 적용 후에는 실제로 누락됐거나 잘못 판단한 항목이 문서에 추가되어야 한다. 결과가 단순한 조언 목록에 그치고 입력, 순서, 실패 조건, 검증 방법이 없다면 Skill로 코드화된 상태가 아니다.

### 6. 검증

다음 항목을 사람이 직접 확인한다.

```text
[ ] 언제 사용하고 언제 중단할지 적혀 있다.
[ ] 필요한 입력을 작업 시작 전에 확인한다.
[ ] 각 단계가 관찰 가능한 행동으로 쓰여 있다.
[ ] 자주 하는 실수와 예외 처리 방법이 있다.
[ ] 완료 여부를 판정할 결과나 체크 절차가 있다.
[ ] 실제 업무 한 건에 적용해 누락과 오판을 기록했다.
[ ] 비용·유지·출시 속도 또는 운영 가드레일을 함께 검토했다.
[ ] 민감 정보와 파괴적 작업을 자동 승인하지 않는다.
```

모든 항목을 만족하고 실제 업무의 담당자가 결과를 검토해야 첫 번째 버전을 완료한 것으로 본다. 이 검증은 특정 도구의 성능을 입증하는 시험이 아니라, 암묵지가 재사용 가능한 절차로 표현됐는지를 확인하는 절차다.

### 7. 대표 오류

- **증상:** 결과가 “주의해서 검토한다” 같은 일반적인 조언에 머문다.
  **원인:** 실제 입력, 판단 순서, 실패 사례를 제공하지 않았다.
  **해결:** 최근 업무 한 건을 기준으로 어떤 자료를 보고 어떤 순서로 결정했는지 다시 인터뷰한다.

- **증상:** 정상적인 예시에서는 작동하지만 예외 상황에서 잘못된 결론을 낸다.
  **원인:** 중단 조건과 사람에게 넘길 조건이 없다.
  **해결:** 정보 부족, 테스트 실패, 권한 부족, 파괴적 변경을 명시적인 중단 조건으로 추가한다.

- **증상:** 문서는 만들어졌지만 실제 업무 시간이 줄지 않고 매번 다시 설명해야 한다.
  **원인:** 입력 형식과 완료 기준이 일정하지 않거나 절차가 실제 작업과 연결되지 않았다.
  **해결:** 한 가지 업무 유형으로 범위를 줄이고, 입력 템플릿과 결과 체크리스트를 고정한 뒤 다시 적용한다.

- **증상:** 에이전트가 기술적으로 가능한 변경을 제안하지만 사업·운영 조건에 맞지 않는다.
  **원인:** 비용, 유지보수, 출시 속도, 구매와 자체 개발 판단, 운영 가드레일이 빠졌다.
  **해결:** 기술 단계마다 사업 영향 질문과 운영 체크리스트를 함께 실행한다.

## 읽을 때 경계

원문은 저자의 경험과 전망을 중심으로 한 글이다. 제시된 작업 시간과 사례는 에이전트 활용 가능성을 보여 주지만, 동일한 업무에서 누구나 같은 결과를 얻는다는 증거는 아니다. 작업의 복잡도, 기존 테스트, 데이터 접근 권한, 규제, 보안 요구, 조직의 검토 절차에 따라 효과는 크게 달라질 수 있다.

원문이 제시하는 “6개월” 같은 전환 시한과 특정 시점의 도구·요금 조건도 보편적인 예측으로 받아들이기 어렵다. 직무가 완전히 사라진다는 실증 자료보다 역할 경계가 이동한다는 저자의 판단에 가깝다.

전문 지식을 Skill로 바꿔도 책임과 검증까지 자동으로 이전되지는 않는다. 잘못된 입력, 빠진 예외, 약한 테스트는 빠른 실행을 빠른 실패로 바꿀 수 있다. 특히 대규모 마이그레이션과 운영 시스템 변경에서는 버전 관리, 테스트, 관측, 백업, 롤백, 사람의 승인이 필요하다.

Hands-on의 인터뷰 프롬프트와 체크리스트는 원문의 방향을 따라 재구성한 실습이며, 원문에 공식 설치 절차나 표준 Skill 규격이 제시된 것은 아니다.
