## 이 문서가 다루는 문제

대부분의 Obsidian–AI 구성은 노트를 읽고 글을 생성하는 데는 쓸 만하다. 그러나 자료가 수개월 또는 수년 쌓인 vault에서 오래된 세부 내용을 찾아 새 자료와 연결하는 일은 단순한 글쓰기와 다르다.

한 vault 안에는 성격이 다른 작업도 공존한다.

- 새 자료를 넣고 이름·링크·메타데이터를 맞추는 일상 작업은 빠르고 저렴해야 한다.
- 여러 시점의 노트를 교차하고 모순이나 패턴을 찾는 종합 작업에는 더 긴 추론이 필요하다.
- 종합의 근거가 되는 오래된 문장을 실제로 찾고 출처를 붙이지 못하면 결과가 그럴듯해도 신뢰하기 어렵다.

모든 작업을 같은 추론 깊이로 처리하면 둘 중 하나를 포기하게 된다. 항상 깊게 추론하면 일상 작업의 비용과 시간이 커지고, 항상 가볍게 처리하면 장기 자료를 엮는 종합이 얕아진다. 컨텍스트 창이 크더라도 필요한 문장을 정확히 검색하지 못하면 이 문제는 해결되지 않는다.

원문은 GPT-6 Astra가 제공한다는 **조절 가능한 effort**와 **장문맥 검색**의 조합을 해법으로 제시한다. 다만 이는 모델의 능력만으로 완성되지 않는다. 연결 방식, 작업별 effort, 인용 규칙과 중단 시 체크포인트까지 함께 설계해야 한다.

## 핵심 개념

### 추론 깊이를 작업에 맞추는 effort

원문에 따르면 Astra는 `low`, `medium`, `high`, `xhigh`, `max`의 다섯 effort 단계를 제공한다. 대부분의 vault 작업은 planning을 곁들인 `medium`에서 시작하고, 낮은 단계가 실패한 근거가 있을 때만 `xhigh`나 `max`로 올리는 것이 원칙이다.

중요한 점은 가장 높은 단계를 계속 쓰는 것이 아니라 **작업 난도에 따라 깊이를 단계적으로 바꾸는 것**이다. 원문은 대화 도중 effort를 바꿔도 캐시가 유지된다고 설명한다. 같은 세션에서 일상 작업을 끝낸 뒤 깊은 종합으로 넘어갈 수 있다는 주장이다.

### 큰 창과 정확한 검색은 다르다

컨텍스트 창은 한 번에 다룰 수 있는 정보량이고, 검색 정확도는 그 안에서 필요한 내용을 다시 찾아내는 능력이다. 큰 vault에서는 “많이 넣을 수 있는가”만큼 “몇 달 전 특정 주장을 정확히 되찾는가”가 중요하다.

원문 작성자는 512K–1M 구간의 장문맥 검색에서 Astra가 96.3%, GPT-5.6 Sol이 73.8%를 기록했다고 주장한다. Astra의 컨텍스트 창은 약 1.1M 토큰으로 Claude Fable 5.1의 1M과 비슷하지만, 실무 차이는 검색 정확도라고 설명한다. 이 수치와 제품 비교는 원문 작성자의 제시값이며 독립적으로 재현하거나 검증한 결과가 아니다.

96.3%도 완벽하지 않다. 원문의 계산대로라면 대략 25번 중 한 번은 놓칠 수 있으므로, 검색 결과에 vault의 출처 노트를 붙이는 규칙이 필요하다.

### 연결 방식은 작업의 성격으로 고른다

원문은 Astra와 Obsidian을 연결하는 방법을 두 가지로 나눈다.

1. **Local REST API와 MCP 스타일 파일 연산:** 모델이 구조화된 도구로 노트를 읽고 검색하고 쓴다. 파일 접근이 결정적이고 지연과 UI 드리프트가 적어 일상 작업의 기본 방식으로 제시된다.
2. **Obsidian UI computer-use:** 모델이 화면을 보고 직접 조작한다. 그래프 뷰, Canvas, API가 없는 플러그인처럼 시각·공간 정보가 필요한 경우에만 쓰는 실험적 방식이다.

MCP(Model Context Protocol)는 모델이 파일 기능을 도구로 호출하게 하는 연결 방식이다. computer-use는 화면 상태에 의존하므로 창 포커스, 배율, 모달 같은 변화에 쉽게 어긋날 수 있다. 파일로 처리할 수 있다면 첫 번째 방식을 기본으로 삼는 것이 원문의 권고다.

## 작동 원리

원문이 제시하는 운영 원리는 effort와 검색을 별개 기능이 아닌 하나의 반복 과정으로 묶는 것이다.

1. 새 노트와 자료를 `medium` effort로 읽고 정리한다.
2. 이름·링크 규칙에 맞춰 기존 노트를 확장하고, 발견한 모순은 덮지 않고 표시한다.
3. 주간 종합처럼 여러 시점의 자료를 교차해야 할 때 같은 세션에서 `high` 또는 `xhigh`로 올린다.
4. 장문맥 검색으로 오래된 주장과 현재 자료의 연결을 찾는다.
5. 종합한 주장마다 근거가 된 vault 노트를 확인한다.
6. 낮은 단계에서 찾지 못한 항목만 더 깊은 검색 대상으로 올린다.
7. 사람이 모순과 해석을 최종 판단하고, 결과를 일정 기간 측정한다.

effort만 조절할 수 있고 검색이 약하면 오래된 근거를 놓친다. 검색만 강하고 effort를 조절할 수 없으면 단순 섭취와 어려운 종합을 같은 비용으로 처리하게 된다. 원문이 Astra와 Obsidian의 조합을 강조하는 이유는 두 레버를 한 과정에서 쓸 수 있다고 보기 때문이다.

높은 effort가 정확성을 자동으로 보장하지는 않는다. 출처 확인이 빠지면 깊은 추론은 오히려 자신감 있는 오종합을 만들 수 있다. 따라서 “출처가 없는 종합은 완료로 보지 않는다”는 규칙이 모델 설정만큼 중요하다.

## 구조와 흐름

원문의 티어 구조를 단순화하면 다음과 같다.

- **Tier 1 — 섭취:** `medium`으로 새 자료를 정리하고 주장과 모순을 표시한다.
- **Tier 2 — 주간 종합:** `high` 또는 `xhigh`로 여러 시점의 노트를 교차한다. 같은 세션의 캐시를 유지하면서 필요한 경우에만 깊이를 높인다.
- **Tier 3 — 심층 검색 시험:** 낮은 티어가 실패한 항목을 대상으로 실제 vault의 오래된 세부 내용을 찾아 인용하게 한다.

한 주 흐름의 원문 사례는 월요일 섭취, 수요일 모순 표시, 일요일 심층 종합으로 이어진다. 일요일 종합은 앞선 단계가 놓친 4개월 전 연결을 찾고, 사람이 그 의미를 확정한다. 핵심은 상시 `max`가 아니라 **낮은 비용의 반복 작업 위에 필요한 순간만 깊은 종합을 얹는 것**이다.

전체 제어 흐름은 다음처럼 정리할 수 있다.

`작업 분류 → 연결 방식 선택 → medium으로 시작 → 검색과 출처 확인 → 실패 근거가 있을 때 effort 상향 → 사람의 판단 → 결과 기록`

세션이 중간에 끝날 가능성도 구조에 포함해야 한다. 원문은 예산이 소진되기 전에 지금까지 확인한 내용과 남은 일을 status 노트에 남겨 다음 세션이 이어받게 하는 체크포인트를 권한다.

## 적용 시나리오

다음은 원문의 주간 운영 사례를 재현 가능한 형태로 구체화한 가상 시나리오다.

- **배경:** 연구자가 수개월간 쌓인 Obsidian vault에 이번 주 자료를 추가하고 있다. 최근 노트의 주장 하나가 과거 기록과 충돌할 가능성이 있다.
- **목표:** 새 자료를 저비용으로 정리한 뒤, 필요할 때만 추론 깊이를 높여 과거 근거와 모순을 찾고 출처가 있는 주간 종합을 만든다.
- **입력:** 이번 주 새 자료와 노트, 이름·링크 규칙, “최근 주장과 충돌하는 과거 기록을 찾아 출처 노트와 함께 요약하라”는 요청.
- **단계:** Local REST API와 파일 연산으로 연결 → `medium`에서 새 자료 섭취 → 모순 후보 표시 → 같은 세션에서 `high` 또는 `xhigh`로 상향 → 오래된 노트 검색 → 관련 노트 인용 → 사람이 충돌 여부 판단.
- **기대 결과:** 새 노트가 기존 규칙에 맞게 정리되고, 주간 종합에는 최근 주장과 연결되는 오래된 노트 및 확인할 모순이 함께 제시된다.
- **실패 조건:** Astra 접근 권한이나 파일 연결이 없거나, 검색 결과에 출처 노트가 없거나, UI 조작의 드리프트로 다른 노트가 선택되거나, 세션이 체크포인트 없이 종료되면 결과를 신뢰하거나 이어가기 어렵다.
- **검증:** 종합에 적힌 각 주장과 연결이 실제 인용 노트에서 확인되는지 대조하고, 미리 정한 오래된 사실 질의 목록에서 정답과 출처를 찾은 비율을 기록한다. 한 번의 성공이 아니라 한 달 동안 비용·누락·수정 횟수를 비교한다.

## Hands-on

원문은 운영 원칙과 일부 설정 메모만 제공하며, Astra 접근부터 Obsidian 연결까지 이어지는 공식 설치 절차나 실행 화면을 제공하지 않는다. 따라서 아래 절차는 **접근 권한과 연결이 이미 준비된 환경에서 tier와 인용 규칙을 시험하는 최소 과정**이다. 완전한 설치 가이드로 사용할 수는 없다.

### 1. 버전

- 런타임: 해당 없음 — 원문은 별도 런타임이나 버전을 지정하지 않는다.
- 도구·라이브러리: 2026년 9월 11일 원문이 지칭한 GPT-6 Astra와 Obsidian. 정확한 제품 버전, 플러그인 버전과 호환 범위는 제시되지 않았다.

### 2. 전제조건

- 계정·권한: 원문은 당시 Astra가 ChatGPT Plus의 Work와 Codex에 있고 일반 Chat 인터페이스에서는 제공되지 않으며, 일반 Chat 접근에는 Pro 플랜이 필요하다고 설명한다. 실제 제공 범위는 계정 화면에서 별도로 확인해야 한다.
- 로컬 환경: 실험용 Obsidian vault 또는 백업된 vault가 필요하다. 쓰기 작업 전에는 대상 범위를 제한하는 편이 안전하다.
- 연결: Local REST API와 MCP 스타일 파일 연산을 사용할 수 있어야 한다. 시각·공간 작업만 computer-use를 사용한다.
- 시험 자료: 최근 노트와, 정답을 알고 있는 수개월 전 노트 한 개 이상을 준비한다.

### 3. 설치

원문이 제시한 설치 관련 정보는 다음 명령 예시뿐이다.

```text
/plugin marketplace add kepano/obsidian-skills
```

원문은 이 명령을 실행할 제품 화면, 선행 플러그인, 권한, 버전, 설치 후 연결 설정을 설명하지 않는다. 이 정보만으로는 안전하게 복사·실행할 수 있는 완전한 설치 절차를 구성할 수 없으므로, 실행 환경이 확인되지 않았다면 명령을 실행하지 않는다.

### 4. 최소 실행

연결이 이미 준비되었다면 정답을 알고 있는 오래된 노트로 다음 순서를 시험한다.

1. `medium`과 planning으로 새 노트 한 개를 읽고 기존 이름·링크 규칙에 맞게 정리하게 한다.
2. 같은 세션에서 “이 주장과 충돌하거나 연결되는 수개월 전 노트를 찾아, 노트 이름과 근거 문장을 함께 제시하라”고 요청한다.
3. 찾지 못했거나 근거가 불충분할 때만 `high` 또는 `xhigh`로 올려 다시 검색하게 한다.
4. 결과의 각 주장에 출처 노트가 있는지 사람이 확인한다.
5. 세션 종료 전에 확인한 내용, 남은 항목과 다음 시작점을 status 노트에 남긴다.

원문에 Astra와 Obsidian을 실제로 연결하는 API 주소, MCP 서버 설정, 인증 값 또는 호출 예시는 없다. 연결되지 않은 환경에서는 이 최소 실행도 재현할 수 없다.

### 5. 예상 결과

- `medium` 단계에서 새 노트가 정해 둔 이름·링크 규칙에 맞게 정리된다.
- 심층 검색 단계에서 미리 준비한 오래된 노트와 근거 문장이 제시된다.
- 찾지 못한 경우에는 근거 없는 종합 대신 누락이 드러난다.
- 체크포인트에는 확인한 내용과 다음 세션에서 이어갈 항목이 남는다.

이 결과는 원문의 운영 가설을 적용했을 때 기대하는 관찰값이다. 특정 성공률이나 비용 절감을 보장하지 않는다.

### 6. 검증

다음 항목을 사람이 직접 대조한다.

- 제시된 노트 이름과 근거 문장이 실제 vault에 존재하는가?
- 오래된 사실 질의의 정답과 출처를 함께 찾았는가?
- `medium`에서 충분했던 작업을 불필요하게 상향하지 않았는가?
- 상향 전후 결과에서 새로 찾은 근거가 무엇인지 구분되는가?
- 출처가 없는 주장을 완료 결과에서 제외했는가?
- 세션이 끝나도 status 노트만으로 작업을 이어갈 수 있는가?

원문은 독립 벤치마크 자료나 공식 검증 명령을 제공하지 않는다. 따라서 96.3%와 제품 간 비교를 이 절차의 합격 기준으로 사용하지 않고, 자신의 vault에서 미리 정답을 아는 질의로 확인한다.

### 7. 대표 오류

- **증상:** 설치 명령이 인식되지 않는다.
  **원인:** 원문이 명령 실행 위치와 필요한 선행 도구를 설명하지 않는다.
  **해결:** 임의의 터미널에서 실행하지 말고, 사용 중인 플러그인 관리자나 도구의 공식 문서에서 명령 지원 여부를 먼저 확인한다.

- **증상:** 깊은 종합이 오래된 내용을 제시하지만 출처 노트가 없다.
  **원인:** 인용 규칙이 빠졌거나 검색이 내용을 놓쳤을 수 있다.
  **해결:** 노트 이름과 근거 문장을 필수 출력으로 요구하고, 확인되지 않은 주장은 결과에서 제외한다.

- **증상:** 모든 작업의 시간과 비용이 커진다.
  **원인:** 일상 섭취까지 `high`, `xhigh` 또는 `max`로 고정했다.
  **해결:** `medium`으로 시작하고 낮은 단계의 실패가 확인된 작업만 상향한다.

- **증상:** computer-use가 다른 노트나 UI 요소를 선택한다.
  **원인:** 창 포커스, 배율, 모달 또는 UI 변경으로 조작 위치가 어긋났다.
  **해결:** 파일 작업은 첫 번째 연결 방식으로 돌리고, 시각·공간 작업은 의미 있는 단계마다 화면 상태를 확인한다.

## 읽을 때 경계

이 문서에 나온 모델 성능, 가격, 접근 조건과 제품 비교는 CyrilXBT가 2026년 9월 11일 원문에서 제시한 내용이다. 공식 제품 문서나 독립적인 실행으로 확인한 결과가 아니며, 이후 제품 정책과 가격이 달라질 수 있다.

- 512K–1M 검색 96.3%와 GPT-5.6 Sol 73.8%는 원문 작성자의 비교 수치다. 시험 방법과 원자료가 제시되지 않아 동일 조건인지 독립적으로 판단할 수 없다.
- 원문은 Astra의 입력·출력 가격을 100만 토큰당 $10/$50, 캐시 읽기를 $1, 입력 272K 초과 시 $20/$75 할증으로 설명한다. 실제 청구 기준은 공식 가격표를 확인해야 한다.
- Claude Fable 5.1이 장기 코딩·연구 지구력과 Terminal-Bench에서 낫고 캐시가 $0.25/M이라는 평가, Kimi K3가 프론트엔드·시각 작업 지향이라 이 vault 패턴에 맞지 않는다는 평가는 원문 작성자의 판단이다.
- Plus Codex 계열 세션이 평범한 작업 약 20분 만에 소진될 수 있다는 내용도 원문의 체감 보고다. 계정과 작업에 따라 달라질 수 있다.
- 96.3%는 매 질문의 성공을 보장하지 않는다. 노트 밀도, 작성 형식과 연결 방식이 다른 개인 vault에서는 결과가 달라질 수 있다.
- Local REST API와 MCP 연결의 세부 설치·인증 절차가 빠져 있어, 원문만으로 처음부터 끝까지 연결을 재현할 수 없다.
- computer-use는 느리고 UI 상태에 따라 드리프트할 수 있다. 그래프, Canvas, API 없는 플러그인처럼 화면이 필요한 작업에만 제한하는 것이 안전하다.
- 한 번의 인상적인 결과는 운영 효과의 증거가 아니다. 원문은 비용, 검색 누락과 사람의 수정량을 한 달 단위로 측정하라고 권한다.
