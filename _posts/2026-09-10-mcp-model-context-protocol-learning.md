## 먼저 잡는 문제

LLM은 똑똑하지만 **바깥 세계와 끊겨 있다**. 책 많이 읽은 천재가 흰 방에 갇힌 비유가 원문의 출발점이다. 바탕화면 PDF 요약, 사내 DB의 티켓 상태처럼 “내 데이터”를 물으면 기본적으로 모른다.

그래서 데이터를 연결해야 하는데, 예전에는 앱마다 **맞춤 API 연동 코드**를 따로 써야 했다. Google Drive용, DB용, Slack용이 제각각이라 지저분하고 보안·유지 비용이 컸다. 그 틈을 메우는 표준이 **MCP(Model Context Protocol)** 다.

## MCP가 무엇인가

원문은 MCP를 **AI의 USB-C** 로 설명한다. 휴대폰마다 충전기가 다르던 시절과, 모델·벤더마다 GitHub 플러그를 따로 만들던 시절이 겹친다. USB-C처럼 **한 번 붙인 포트**로 여러 기기(여러 AI)가 같은 규칙으로 이야기하게 만드는 오픈 소스 표준이다.

요점만 말하면: AI가 데이터를 **어떻게 요청할지**, 데이터 쪽이 **어떻게 답할지** 의 공통 규칙을 정한다. 데이터에 MCP 포트를 달아 두면, MCP를 말하는 모델은 그 포트에 바로 붙을 수 있다. 모델마다 glue code를 다시 쓰는 부담을 줄이는 쪽이다.

## 세 부품: Host · Client · Server

원문이 보안의 기초로 강조하는 구조다.

1. **MCP Host** — 화면에 보이는 AI 앱. 예: Claude Desktop, Cursor 같은 IDE. 모델이 들어가 있고, 프롬프트를 받아 “밖에 물어봐야 하나”를 판단한다.
2. **MCP Client** — Host 안의 “USB-C 케이블”. 모델이 바깥 데이터가 필요하다고 하면 Client가 연결을 연다.
3. **MCP Server** — 데이터·도구 쪽 문지기. DB, 파일, API 앞에 서서 허용된 일만 수행하고 결과를 돌려준다.

모델이 DB를 **직접** 만지지 않고, Server를 통해서만 말한다는 점이 이후 보안 이야기의 축이다.

## 세 능력: Resources · Prompts · Tools

Server가 AI에게 줄 수 있는 능력은 세 종류로 나뉜다.

| 능력 | 한 줄 | 비유(원문) |
|---|---|---|
| **Resources** | 읽기 전용 데이터 | 보고서에 쓰라고 준 PDF — 읽되 낙서 금지 |
| **Prompts** | 미리 다듬어 둔 프롬프트·워크플로 템플릿 | 같은 질문을 매번 잘 던지게 돕는 안내서 |
| **Tools** | 실행 가능한 동작 | 검색, 쿼리, 파일 쓰기처럼 “손을 쓰는” 일 |

학습할 때 헷갈리기 쉬운 경계: Resource는 **보기**, Tool은 **하기**. Prompt는 둘을 잘 쓰게 만드는 **말해 주는 방식**에 가깝다.

## 초보·솔로에게 왜 중요한가

원문은 대기업 전용이 아니라고 말한다. 핵심은 **한 번 서버를 만들면** Claude·OpenAI·로컬 모델 등 MCP를 말하는 쪽에 다시 붙일 수 있다는 점이다. 모델이 바뀔 때마다 연동을 다시 짜는 비용을 줄인다.

## 보안: 서버가 보디가드인 이유

“재무 DB에 연결하면 AI가 테이블을 지우거나 밖으로 메일을 보내지 않나?” 라는 질문에, 원문은 **Server가 보디(bouncer)** 라고 답한다. 모델은 Server에만 요청하고, 개발자가 Server에 “SELECT만 허용, DELETE 거절” 같은 규칙을 둔다. 구조상 **권한이 Server에 모인다** 는 학습 포인트다. (원문이 “절대 안전”이라고 단정하는 문장으로 읽지는 말 것 — 설계 책임이 Server 쪽에 있다는 이야기다.)

## 쓰임(개념만)

- **코딩 Host + 로컬 도구**: 저장소·터미널에 연결된 Tool로 버그 찾기·수정·테스트까지 이어가기.
- **사내 오라클**: Notion·GitLab·고객 DB처럼 흩어진 소스를 Server들로 묶고, 한 Host에서 질문하기.
- **개인 워크플로**: 로컬 파일·캘린더·메신저 등도 같은 플러그 모델로 붙이기.

세부는 제품마다 다르니, 여기서는 “Host가 여러 Server Tool을 고른다” 정도만 남긴다.

## MCP와 RAG는 같은가

아니다. 원문 구분:

- **RAG** — 문서를 잘라 벡터로 넣고, 의미 검색으로 조각을 가져오는 **전용 파이프라인**.
- **MCP** — 청킹·벡터화가 아니다. **문(doorway)** 이다.

그래서 RAG 파이프라인 **앞에** MCP Server를 두고 `Search_Internal_Documents` 같은 Tool로 감쌀 수 있다. AI는 벡터 수학을 몰라도 되고, “문서 찾는 도구”만 알면 된다. 모듈 분리가 학습 포인트다.

## 데이터가 오가는 방식(개념)

에이전트는 HTTP처럼 한 번 요청하고 끊기는 패턴과 잘 안 맞는다. 생각 → 도구 → 다시 생각의 왕복이 많다. 원문은 대표 전송으로 **Stdio**(로컬·터미널과 같은 입출력)와, 원격·지속 대화에 맞는 다른 전송층을 함께 언급한다. 초보 단계에서는 “로컬은 Stdio가 흔하다” 정도면 충분하다.

## 남는 한 줄

외운 천재(고립 모델)에서, **필요할 때 정확한 데이터를 가져오는 연결된 워커** 로 옮기자는 이야기가 원문의 미래상이다. MCP는 그 연결을 **표준 언어**로 만들려는 축이다.
