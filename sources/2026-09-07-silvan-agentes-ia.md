# AGENTES IA: LA GUÍA COMPLETA (monetiza hoy) — AI 에이전트 완전 가이드 (오늘부터 수익화)

같은 달에 두 사람이 AI 에이전트를 발견한다.

한 사람은 몇 주 동안 데모를 돌려 보고, “이 에이전트가 하는 일 좀 봐” 같은 스레드만 읽으면서도 그 아래(function calling, 오케스트레이션(orquestación), 영속 메모리(memoria persistente))가 무엇인지 이해하지 못한다. 그래서 마케팅 층을 넘지 못한다. 다른 한 사람은 에이전트가 기술적으로는 도구와 상태에 접근하는 **추론 루프(loop de razonamiento)** 라는 것을 이해했고, 첫 주부터 인프라로 팔기 시작했다.

차이는 재능이 아니다. 두 번째 사람이 실제 비즈니스가 무엇을 필요로 하는지 진단할 만큼 아키텍처를 이해했다는 점이다. 유튜브 데모를 되풀이하는 수준이 아니다.

이 가이드는 일부러 길고 기술적이다. LLM이 무엇인지는 알지만 프로덕션에서 에이전트를 짜 본 적이 없다면, 흩어진 도구 목록이 아니라 **전체 지도**가 필요하다. 아키텍처, 스택, 무엇을 청구할지, 첫 고객을 어디서 얻을지, 미리 보지 않으면 한 달을 날릴 기술적 실수들.

저장해 두라. 한 번 이상 다시 열게 될 것이다.

이 가이드에는 청구하기 전 아키텍처 복잡도가 낮은 쪽에서 높은 쪽으로 **여섯 단계(nivel)** 가 있고, 끝에 흔한 기술적 실수와 카테고리별 스택이 있다.

---

## TL;DR 기술 요약

**에이전트 = LLM + tool calling + 실행 루프(loop de ejecución) + 메모리/상태.** 이 네 조각이 없으면 긴 프롬프트가 달린 챗봇이지, 에이전트가 아니다.

첫날부터 100% 자율 에이전트가 아니라, **결정론적 자동화(automatización determinística)** (n8n/Make) + 임계 지점의 **AI tool call 하나**로 시작하라. 오류 표면이 작고, 팔기도 쉽다.

**MCP (Model Context Protocol)** 는 Anthropic, Google, OpenAI가 채택 중인, 에이전트를 외부 도구에 연결하는 표준이다. 오늘 배우는 것은 과장이 아니라 실질적인 경쟁 우위다.

“네 비즈니스에 GPT-5/Claude를 붙였다”고 팔지 마라. **SLA** 를 팔아라. 응답 시간, 해결률, 주당 절약한 사람 시간.

**RAG (retrieval-augmented generation)** 는 여전히 버티컬 에이전트를 쓸모 있게 만드는 일의 약 80%다. 잘 색인된 지식 베이스가, 고르는 모델보다 더 중요하다.

관측 가능성(observability) — 로그, 트레이싱(tracing), 평가(evals) — 이 없는 에이전트는 제품이 아니라 데모다. 월 구독을 내는 고객은, 에이전트가 실패할 때 **당신이 보고 있다**는 것을 볼 수 있어야 한다.

가장 높은 티켓은 **멀티에이전트 + 기업의 레거시 시스템(ERP, 자체 CRM)과의 깊은 통합**에 있다. 거기서는 어떤 노코드 빌더도 경쟁하지 못한다.

첫 고객부터 프롬프트와 플로우를 **코드처럼 버전 관리**하라. 오늘 textarea 안의 프롬프트가, 내일은 통제하지 않으면 프로덕션에서 깨지는 파이프라인이 된다.

## 레벨 0: 무엇을 고르기 전의 최소 아키텍처

아무것도 팔기 전에, 실제 에이전트를 구성하는 조각을 이해하라.

**에이전틱 루프(loop agéntico).** 에이전트는 “대답하는 프롬프트”가 아니다. 목표를 달성하거나 스텝 한도에 이를 때까지 반복되는 **지각 → 추론 → 행동 → 관찰** 사이클이다. 모델이 어떤 도구를 호출할지 정하고, 도구가 결과를 돌려주고, 모델이 다음 스텝을 정한다. 이 루프가 없으면 챗봇이다.

**Tool calling / function calling.** 모델이 실제 코드를 실행하게 해 주는 것이다. API 조회, DB 쓰기, 메일 발송. 각 도구는 스키마(이름, 파라미터, 설명)로 정의되고, 모델은 그 스키마로 언제·어떻게 호출할지 정한다.

**MCP (Model Context Protocol).** Anthropic이 밀고, Google(Gemini Spark) 등이 이미 채택한 개방 표준이다. 도구와 데이터 소스를 에이전트에 **균일한 방식**으로 노출해, 모델마다 통합을 다시 쓰지 않게 한다. 한 고객 이상 오래 쓸 에이전트를 만들 거라면, 도구를 MCP로 노출하는 법을 배우는 것이 모델·공급자를 바꿀 때 전체를 다시 쓰는 비용을 줄여 준다.

**메모리와 상태.** 단기(현재 대화 컨텍스트) vs. 장기(그 사용자와의 과거 상호작용 — 보통 벡터 DB 또는 키-값 스토어). 영속 메모리가 없으면 세션마다 같은 질문을 반복하고, 그게 최종 사용자 불만 1위다.

**RAG.** 에이전트가 추론하기 전에 올바른 데이터가 필요하다. RAG는 고객의 지식 베이스(문서, FAQ, 카탈로그)를 벡터 DB에 색인하고, 질의마다 관련 조각을 가져와 모델 컨텍스트에 넣는다. 잘못된 **청킹(chunking)** 이나 잘못된 **임베딩(embedding)** 은, 기술적으로 “동작하는” 에이전트도 망가뜨린다.

시장 잠재력으로 유스케이스를 고르지 말고, **도메인 우위**로 고르라. 이미 운영 흐름을 아는 업종(물류, 헬스케어, 법률)에서 가장 좋은 에이전트를 설계한다. 무엇을 물을지, 무엇이 깨질지 알기 때문이다.

아키텍처보다 먼저 **측정 가능한 결과**를 정의하라. “AI 에이전트를 붙여 드립니다”는 안 팔린다. “첫 응답 시간을 4시간에서 2분으로 줄이고, 모델 신뢰도가 X% 아래로 떨어지면 사람에게 자동 에스컬레이션합니다”는 팔린다. 지표가 있기 때문이다.

첫 고객부터 **돈을 받아라.** 포트폴리오용 무료 에이전트는 프로덕션 피드백이 아니라 데모 피드백을 준다. 둘은 다르다.

## 레벨 1: 자동화 + AI tool call 하나 (이번 주에 청구할 수 있는 것)

첫 수입에 복잡한 에이전트 프레임워크는 필요 없다. 전통 자동화의 결정론적 플로우에, LLM이 맡는 **지능형 결정 지점 하나**면 된다.

**의도 분류가 있는 1차 응대 봇.** webhook이 WhatsApp/채팅 메시지를 받고, LLM이 function calling으로 의도(가격 문의, 주문 상태, 불만)를 분류한 뒤, 결정론적 플로우가 해당 액션을 실행하거나 사람에게 넘긴다. 전형적 스택: 오케스트레이터로 n8n 또는 Make, 분류용 API 모델, 동적 응답용 비즈니스 DB 연동. **응답 시간 SLA**가 있는 월 구독으로 청구하라.

**기본 RAG가 있는 리서치·요약 에이전트.** 변호사, 컨설턴트, 분석가용. 판례·보고서·계약을 단순 벡터 DB에 색인하고, 정확한 출처를 인용하며 질문에 답한다. 여기서 기술적으로 중요한 것은 **올바른 청킹**이다. 법률 문서는 조항/조문 맥락을 지키는 청크가 필요하고, N 토큰마다 임의로 자르면 안 된다.

**스코어링이 있는 리드 자격 파이프라인.** 에이전트가 채팅으로 구조화된 질문 3–4개를 하고, structured output / JSON mode로 엔티티(예산, 긴급도, 제품 유형)를 뽑은 뒤, 점수로 사람에게 넘길지 자동 너처링에 둘지 정한다. ROI가 직접적이라 팔기 쉽다. 영업팀이 차가운 리드에 쓰는 시간이 줄어든다.

**상태 기반 트리거의 팔로업 에이전트.** CRM이나 예약 DB에 연결해, 고정 크론이 아니라 **레코드 상태**에 따라 리마인더, 일정 변경, 판매 후 팔로업을 쏜다. 기술 핵심은 상태 처리다. 다음 액션을 정하기 전에 현재 상태를 읽어야 하고, 크론만 돌리면 안 된다.

**첫 고객을 얻는 법:** 막연한 “AI 에이전트”를 제안하지 마라. 구체 비즈니스에서 **측정 가능한 병목**(응답 시간, 이탈률, 반복 작업에 쓰는 팀 시간)을 진단하고, 그걸 푸는 **구체 플로우**를 제안하라.

## 레벨 2: 플로우에서 패키지 제품으로

같은 버티컬에 같은 유형의 에이전트를 여러 번 만들었다면, **재사용 가능한 기술 제품**으로 패키징하라.

**변수로 파라미터화한 플로우 템플릿.** n8n/Make에서 전체 플로우(webhook → LLM 분류 → 액션 → 로깅)를 템플릿으로 내보내, 고객은 API 자격증명과 지식 베이스만 넣는다. 설계 비용은 이미 회수됐고, 다음 판매는 거의 순마진이다.

**버티컬용 프롬프트 + function calling 스키마 키트.** 시스템 프롬프트, few-shot 예제, 이미 검증·조정된 함수 스키마를 업종별(부동산, 헬스케어, 법률)로. 리포나 쓰는 도구에 가져올 수 있는 컬렉션으로 묶는다.

**산업별 RAG용 사전 구조화 지식 베이스.** 예를 들어 부동산 카탈로그에 최적의 청킹과 메타데이터 스키마를 이미 풀었다면, 그게 제품이다. 데이터만이 아니라 **색인 구조**다.

**당신 스택에 대한 미니 기술 교육.** 오케스트레이터 + 모델 + 벡터 DB + observability로 파이프라인을 짠 방식을 단계별로 문서화. 같은 길을 시행착오 없이 가고 싶은 사람에게 짧은 코스로 팔 수 있다.

**파는 곳:** 인포제품 플랫폼, 유료 접근 비공개 리포, 또는 더 정교한 투자 전에 수요를 검증하는 동안의 수동 전달.

## 레벨 3: 혼자 도는 시스템 (연속 모니터링 에이전트)

목표는 “내가 매번 실행을 누르지 않아도 시스템이 가치를 만든다”다. 스케줄 잡, 이벤트 트리거, 사람 감독 없이 견디는 오류 처리가 필요하다.

**알림이 있는 24/7 모니터링 에이전트.** 크론 잡 또는 이벤트 리스너가 에이전트를 돌려 소스(경쟁 가격, 브랜드 멘션, 규제 변화)를 보고, 저장된 이전 상태와 비교한 뒤, **관련 변화가 있을 때만** 알린다. 알리기 전에 LLM 검증 한 번으로 오탐을 줄인다. 구독으로 수익화한다.

**자동 리서치 파이프라인이 있는 뉴스레터/채널.** 니치 소스의 스크래핑 또는 API 소비 → 요약·관련도 랭킹 에이전트 → 당신이 검토하고 각도를 준 뒤 발행. 기술 핵심은 최종 문장이 아니라 **수집·중복 제거 파이프라인**이다.

**에이전트 도구 기술 분석 계정 + 제휴.** 같은 테스트 케이스를 여러 플랫폼(n8n vs. Make vs. LangGraph나 Claude Agent SDK 같은 에이전트 프레임워크)에 돌려 자체 벤치마크를 내고, 방법론을 밝혀 공개한다. 기술적 엄밀함이 일반 콘텐츠와 가르는 지점이다.

이 레벨의 전형적 기술 실수: **실패한 실행을 로그하지 않는 것.** 무인으로 도는 시스템이면, 무언가 깨졌을 때 **당신 자신**에게 알리는 채널이 필요하다. 아니면 고객이 먼저 발견한다.

## 레벨 4: 깊은 통합 (높은 티켓이 있는 곳)

고객의 시스템 아키텍처를 이해해야 한다. 고립된 에이전트만 짜는 수준이 아니다. 레벨 1 고객 열 명분의 가치가 한 고객에 있을 수 있는 단계다.

**레거시 시스템(ERP/자체 CRM)과 에이전트 통합.** 현대 API가 없는 시스템에 붙이려면 UI 자동화인 **RPA** 와 function calling을 섞거나, 자체 미들웨어를 짜야 할 때가 있다. 문제는 프롬프팅이 아니라 시스템 통합이라, 노코드 빌더 경쟁이 사라진다.

**복잡한 프로세스용 멀티에이전트 아키텍처.** 오케스트레이터 에이전트가 전문 에이전트(데이터 조회, 초안 작성, 비즈니스 규칙 검증)에 하위 작업을 위임하고, LangGraph, CrewAI, 또는 Anthropic 에이전트 SDK 같은 프레임워크로 조율한다. 여기서 비싸게 받는 것은 **결정 그래프 설계와 부분 실패 처리**다.

**에이전틱 AI 성숙도 기술 감사.** 어떤 프로세스가 오늘 에이전트로 자동화 가능한지 vs. 먼저 데이터 정리나 API 노출이 필요한지 진단. 산출물은 아이디어 목록이 아니라 **제안 아키텍처가 있는 구현 계획**이다.

**관측 가능성(observability)을 서비스로 하는 유지보수.** 트레이싱 대시보드(어떤 도구를 호출했는지, 지연, 오류율), 프롬프트를 바꿀 때 회귀를 돌리는 자동 evals, 품질 저하 알림. LLM 엔지니어링과 DevOps를 둘 다 이해해야 해서, 자체 서비스로 거의 아무도 안 파는 **반복 매출**이다.

여기 들어가려면 시니어 ML 엔지니어일 필요는 없다. 다만 남의 API 문서를 읽고, 인증(OAuth, API 키, 서명된 webhook)을 이해하며, 분산 시스템의 **부분 실패**를 추론할 수 있어야 한다.

## 레벨 5: 자기 시스템으로 만들기

고객이 여러 명이거나 혼자 도는 제품이 있으면, 일이 바뀐다. “에이전트 만들기”에서 “아키텍처가 **당신 혼자에 의존하지 않고** 복제되게 하기”로.

첫 고객부터 프롬프트·스키마·플로우를 **코드처럼 버전 관리**하라 (git, textarea 아님). 버전 없이 바뀌는 프롬프트가 “지난주엔 잘 되던 에이전트가 지금은 왜 이러는지 모르겠다”의 1번 원인이다.

버티컬별 **내부 템플릿 프레임워크**를 짜서, 매번 아키텍처를 다시 설계하지 않게 하라. 처음엔 일주일이 걸리던 일이 다섯 번째엔 하루여야 한다.

기술 용량 포화감이 오기 **전에** 가격을 올려라. 시간 부족으로 같은 버그를 반복 고치고 있다면, 이전 가격은 이미 너무 낮다.

청구액만이 아니라 **고객당 실제 비용**(소비 토큰, 유지보수 시간, 인시던트)을 재라. 컨텍스트를 많이 먹고 자주 실패하는 에이전트 한 고객이, 레벨 1의 단순한 고객 세 명보다 나쁜 사업일 수 있다.

## 가장 흔한 기술적 실수

긴 프롬프트를 에이전트와 혼동하기. tool calling과 결정 루프가 없으면 실제 자율성이 없다.

스텝 한도와 비용 한도를 두지 않기. 반복 한도 없는 에이전트는 루프에 빠져 토큰 예산을 태우고, 청구서가 올 때까지 아무도 모를 수 있다.

고객이 항의할 때까지 observability를 무시하기. 로그·트레이싱이 없으면 프로덕션 디버깅은 추측이다.

구조적 맥락이 중요한 도메인(법률, 의료, 기술)에 일반 청킹 RAG를 쓰기.

프롬프트와 플로우를 코드가 아니라 버릴 설정처럼 다루며 버전 관리하지 않기.

결정론적 단순 자동화로 풀리는 문제에 복잡한 멀티에이전트 아키텍처를 원하기. 모든 것에 자율성이 필요하지는 않다.

## 카테고리별 기술 스택

**모델과 API:** Claude, GPT, Gemini를 API로, 네이티브 function calling / structured output과 함께.

**에이전트 오케스트레이션:** LangGraph, CrewAI, 또는 공급자 자체 에이전트 SDK(Claude Agent SDK) — 다단계 추론 플로우용.

**결정론적 층으로서의 노코드 자동화:** n8n, Make, Zapier. 추론이 필요 없는 일은 여기 두고, LLM은 결정 지점에만.

**도구 프로토콜:** MCP — 도구/데이터를 모델·고객 간에 재사용 가능하게 노출.

**RAG용 벡터 DB:** Pinecone, Weaviate, pgvector — 데이터 양과 이미 Postgres가 있는지에 따라.

**영속 메모리:** 일반 지식 RAG와 분리된, 사용자 메모리 전용 키-값 또는 벡터 스토어.

**Observability와 evals:** LangSmith류 LLM 트레이싱으로 실행·지연·오류율 로깅, 프롬프트 변경 전 회귀 eval 세트.

**버전 관리:** 프롬프트, 함수 스키마, 내보낸 플로우를 git으로. 흩어진 문서가 아니라.

## 마무리

이 레벨들 중 어느 것도 ML 엔지니어일 것을 요구하지 않는다. 잘 진단할 만큼 아키텍처를 이해하고, 이미 도메인 우위가 있는 유스케이스를 고르며, “AI”라는 단어가 아니라 **지표**로 파는 것이 필요하다.

이번 주 레벨 1부터 시작하라. LLM 결정 지점 하나짜리 결정론적 플로우, 측정 가능하고, 첫날부터 청구한다.
